# [v0.4] 产值核算与回款逻辑闭环

> 本轮聚焦**产值分配 + 回款**两条核心业务的闭环。基于 v0.2（《系统调整分析文档》）的实现做矫正与扩展，引入"效益分阶段计入"和"修正机制"。
>
> 编写时间：2026-04-25
> 范围：合同收费模型、阶段产值计算、产值分配、回款应收、季度还原；不涉及 OA / 工资发放 / 领导分成（这些已确认下线或外置）。

---

## 一、规则总结（来自客户最新口径）

### 1.1 收费模型

| 模型 | 说明 | 计算 |
| --- | --- | --- |
| **基本收费**（contract_type=0） | 固定收费，无论结果如何，提供服务即收 | `应收 = base_amount × Σ 已完成阶段 stage_output%` |
| **基本+效益**（contract_type=1） | 基本部分固定 + 效益部分按服务成果（如审减额、节约额）×约定比例 | `应收 = 基本部分 + 效益部分（分阶段累计计入）` |

### 1.2 产值拆分

```
阶段产值（本期新增）
├── 员工池 = 阶段产值 × 40%
│      ├── 每人正常 ≈ 8.06%（of 阶段产值，含奖金）
│      └── 降档 4%（差额 4.06% 全归公司）
└── 公司账 = 阶段产值 × 60%
       + 降档差额（含未做好部分）
       + 离职成员未发金额
       + 公司补贴（只记不算入总额，独立核算）
```

**重要**：
- 比例方向**与 v0.2 文档相反**：v0.2 写的是"公司 40% / 员工 60%"，**正确为"员工 40% / 公司 60%"**
- 不再单独区分"领导兜底"——所有非员工实得的钱**全部归公司账**（`领导分成不考虑`）
- `dist_type=2 领导兜底` **取消使用**

### 1.3 效益分阶段计入

效益部分**不一次性计入**，按阶段累计释放。每个阶段绑定一个 `benefit_inclusion_ratio`（累计%）。

**示例**：基本 10 万 + 预计效益 20 万 → 最终效益 25 万

| 阶段实例 | base 累计% | benefit 累计% | 当时 benefit_amount | 累计应得 | 本期产值 |
| --- | --- | --- | --- | --- | --- |
| 阶段 1 验收 | 3% | 0% | — | 0.3 万 | 0.3 万 |
| 阶段 2 验收 | 46% | 0% | — | 4.6 万 | 4.3 万 |
| 阶段 2 完成 | 100% | 10% | 20 万 | 12 万 | 7.4 万 |
| 阶段 3 验收 | 100% | 30% | 20 万 | 16 万 | 4 万 |
| 阶段 4 验收 | 100% | 70% | 20 万 | 24 万 | 8 万 |
| 阶段 5 验收 | 100% | 100% | 25 万（最终） | 35 万 | 11 万 |

**通用公式**：

```
本阶段累计应得 = contract.base_amount × stage.stage_output / 100
              + contract.benefit_amount × stage.benefit_inclusion_ratio / 100

本期产值 = 本阶段累计 - 上一次产值分配单累计

修正机制：每次效益值变化时，通过"效益修正"操作记录历史；下一次创建产值分配单时
        自动用最新 benefit_amount 重算累计；本期 = 当前累计 - 历史最大累计 →
        自动多退少补
```

### 1.4 季度还原（取代"工资发放"）

- **没有"工资发放"概念**
- 产值分配按季度归集 → 现有 `PerformanceRestoreService`（绩效还原）方向正确，**保持不变**
- 财务在季度末按生成的"应还原列表"打款 → 标记已还原即闭环

## 二、与 v0.2 的差异

| 维度 | v0.2 | v0.4 |
| --- | --- | --- |
| 员工池比例 | 60% | **40%** |
| 公司池比例 | 40% | **60%** |
| 阶段产值计算 | 一次性等于 totalAmount（前端手填） | 系统按"基本累计 + 效益累计"自动算 |
| 效益规则 | 自由文本字段，**没用** | 结构化字段 + 阶段计入比例 + 修正历史 |
| 领导兜底 | 单独字段 `leader_extra` | **并入 `company_reserve`**，字段保留但语义改 |
| 离职兜底 | 单独字段 `other_amount` | 保留独立字段（便于追溯），但归公司账 |
| 工资发放 | 待后续迭代 | **取消**，季度还原即闭环 |
| 应收（回款） | 仅看 `contract_amount × Σ 已完成 stage_output%` | 基本+效益项目要叠加效益部分 |

## 三、数据库改动

### 3.1 `contract` 表加效益金额字段

```sql
ALTER TABLE contract
  ADD COLUMN benefit_amount     decimal(20, 2) NULL COMMENT '当前预计效益金额（最新值，分阶段计入）',
  ADD COLUMN benefit_status     tinyint DEFAULT 0 NOT NULL COMMENT '0-预计中/1-已最终确认',
  ADD INDEX idx_contract_benefit_status (benefit_status);
```

**字段语义**：
- `benefit_amount`：随效益修正而更新，是**最新值**；历史值在 `contract_benefit_revision`
- `benefit_status=1` 表示项目已结算，效益值不再变；产值分配单创建时校验
- `benefit_rules`（v0.2 已有的自由文本）保留，仅作描述说明；不再影响计算

### 3.2 新建 `contract_benefit_revision`（效益修正历史）

```sql
CREATE TABLE contract_benefit_revision (
    revision_id      bigint NOT NULL COMMENT '修正id' PRIMARY KEY,
    contract_id      bigint NOT NULL COMMENT '合同id',
    old_amount       decimal(20, 2) NULL COMMENT '修正前金额（首次为空）',
    new_amount       decimal(20, 2) NOT NULL COMMENT '修正后金额',
    delta_amount     decimal(20, 2) NULL COMMENT '差额（new - old），首次为空',
    revision_reason  varchar(512) NULL COMMENT '修正原因',
    is_final         tinyint DEFAULT 0 NOT NULL COMMENT '是否最终确认（结算时填 1，与 contract.benefit_status 联动）',
    operator_id      bigint NULL COMMENT '操作人',
    created_time     datetime DEFAULT CURRENT_TIMESTAMP NOT NULL,
    is_delete        tinyint DEFAULT 0 NOT NULL,
    KEY idx_cbr_contract (contract_id),
    KEY idx_cbr_created (created_time)
) COMMENT '合同效益预测修正历史';
```

**业务约束**：
- `is_final=1` 的修正写入后，`contract.benefit_status` 同步置 1
- 已有 `is_final=1` 历史时，新增修正必须 `is_final=0` 或拒绝（结算后不可改）

### 3.3 `project_stage` 加效益计入比例

```sql
ALTER TABLE project_stage
  ADD COLUMN benefit_inclusion_ratio decimal(6, 4) DEFAULT 0.0000 NOT NULL
    COMMENT '效益部分累计计入比例（%，0-100）',
  ADD COLUMN base_inclusion_note varchar(64) NULL
    COMMENT 'stage_output 用作"基本部分累计计入比例"，本字段冗余说明';
```

**注意**：复用现有的 `stage_output` 字段作为**基本部分累计%**（与 v0.2 一致），**新增**`benefit_inclusion_ratio` 字段作为**效益部分累计%**。两者各自独立维护。

### 3.4 `output_value` 加阶段累计快照

```sql
ALTER TABLE output_value
  ADD COLUMN stage_cumulative_amount     decimal(20, 2) NULL
    COMMENT '当前阶段累计应得（含基本+效益）',
  ADD COLUMN previous_cumulative_amount  decimal(20, 2) NULL
    COMMENT '上一次产值分配单的累计（差值即本期 totalAmount）',
  ADD COLUMN base_amount_part            decimal(20, 2) NULL
    COMMENT '本期基本部分',
  ADD COLUMN benefit_amount_part         decimal(20, 2) NULL
    COMMENT '本期效益部分',
  ADD COLUMN benefit_snapshot            decimal(20, 2) NULL
    COMMENT '快照：本单创建时的 benefit_amount';
```

**用途**：
- `stage_cumulative_amount - previous_cumulative_amount = totalAmount`（本期产值）
- `base_amount_part + benefit_amount_part = totalAmount`
- `benefit_snapshot` 用于事后审计：能解释"为什么本单产值是这个数"

### 3.5 `output_value_distribution.dist_type` 语义更新

注释更新（无需改字段）：

```
0-员工正常
1-员工降档
2-（已废弃）
3-（保留语义但不在分配单创建时生成）
4-离职兜底
```

## 四、产值核算服务重写

### 4.1 创建产值分配单的新流程

```
入参：projectStageId（必须）+ 季度 + 分配明细 + 公司补贴
     （totalAmount 不再由用户填，由系统算出）

1. 查 stage / project / contract
2. 查同一项目的所有"已确认（status>=2）"产值分配单，取最大 stage_cumulative_amount
   作为 previousCumulativeAmount（首单为 0）
3. 计算 currentCumulativeAmount：
   - basePart = contract.base_amount × stage.stage_output / 100
   - benefitPart = contract.benefit_amount × stage.benefit_inclusion_ratio / 100
   - currentCumulativeAmount = basePart + benefitPart
4. totalAmount = currentCumulativeAmount - previousCumulativeAmount
   - 校验：totalAmount > 0（如等于 0，提示用户：本阶段未产生新产值）
   - 修正回退场景：若 < 0（极少见，效益值大幅下调），需财务确认是否生成"负产值单"
5. 校验 40%/60% 拆分（与 v0.2 一致，但比例对调）
6. 落 output_value + output_value_distribution
7. 守恒：companyAccount + Σ员工实得 = totalAmount
   - companyAccount = totalAmount × 60% + 降档差额 + 离职兜底
```

### 4.2 关键代码变更（`OutputValueServiceImpl.java`）

```java
// 比例对调
private static final BigDecimal COMPANY_RESERVE_RATE = new BigDecimal("60");  // was 40
private static final BigDecimal PERSONAL_POOL_RATE   = new BigDecimal("40");  // was 60

// 不再接受用户填的 totalAmount，改为系统算
public Long createOutputValue(CreateOutputValueDto dto, Long userId) {
    // 1. 系统算 totalAmount
    StageCumulativeResult cumulative = calcStageCumulative(dto.getProjectStageId());
    BigDecimal totalAmount = cumulative.current.subtract(cumulative.previous);

    if (totalAmount.signum() < 0) {
        throw new BusinessException(...,
            "效益值下调导致本期产值为负 " + totalAmount + "，请确认或先做效益修正");
    }
    if (totalAmount.signum() == 0) {
        throw new BusinessException(...,
            "本阶段累计与上次相同，无新增产值，无需创建分配单");
    }

    // 2. 比例（按 v0.4 矫正后的）拆分
    BigDecimal companyAccount = totalAmount.multiply(COMPANY_RESERVE_RATE).divide(BD_100, 2, HALF_UP);
    BigDecimal employeePool   = totalAmount.multiply(PERSONAL_POOL_RATE).divide(BD_100, 2, HALF_UP);

    // 3. 逐人算（与 v0.2 一致，allocRatio 现在是"在 40% 池里的占比"）
    //    8.06% of 总额 ≈ 20.15% in 40% 池——前端 UI 提示
    //    降档差额 → 加进 companyAccount
    //    离职兜底 → 加进 companyAccount（但保留 dist_type=4 行便于追溯）
    // ...

    // 4. 保存（带阶段累计快照）
    OutputValue ov = OutputValue.builder()
        .totalAmount(totalAmount)
        .stageCumulativeAmount(cumulative.current)
        .previousCumulativeAmount(cumulative.previous)
        .baseAmountPart(cumulative.basePart)
        .benefitAmountPart(cumulative.benefitPart)
        .benefitSnapshot(cumulative.benefitAmountUsed)
        .companyReserve(companyAccount)  // 含降档差额 + 离职兜底
        .otherAmount(otherAmount)         // 保留独立字段以便审计，但 companyAccount 已含
        .leaderExtra(BigDecimal.ZERO)     // 不再生成
        // ...
        .build();
}

private StageCumulativeResult calcStageCumulative(Long stageId) {
    ProjectStage stage = projectStageService.getProjectStageById(stageId);
    Contract contract = contractService.getContractByProjectId(stage.getProjectId());

    BigDecimal baseAmt = contract.getBaseAmount() != null
        ? contract.getBaseAmount() : contract.getContractAmount();  // 老数据兜底
    BigDecimal benefitAmt = contract.getBenefitAmount() != null
        ? contract.getBenefitAmount() : BigDecimal.ZERO;

    BigDecimal basePart = baseAmt.multiply(stage.getStageOutput()).divide(BD_100, 2, HALF_UP);
    BigDecimal benefitPart = benefitAmt.multiply(stage.getBenefitInclusionRatio()).divide(BD_100, 2, HALF_UP);
    BigDecimal currentCumulative = basePart.add(benefitPart);

    BigDecimal previousCumulative = outputValueMapper.findMaxCumulativeByProject(stage.getProjectId());

    return new StageCumulativeResult(currentCumulative, previousCumulative,
        basePart, benefitPart, benefitAmt);
}
```

### 4.3 公司账归集

`output_value` 主表上：

| 字段 | 现状 | v0.4 |
| --- | --- | --- |
| `total_amount` | 用户填的总额 | 系统算的本期产值（new） |

## 五、回款 / 应收逻辑改动（CollectionService）

### 5.1 应收公式

```java
private BigDecimal calcExpectedAmount(Contract contract, List<ProjectStage> stages) {
    if (contract == null) return BigDecimal.ZERO;
    if (stages == null || stages.isEmpty()) return BigDecimal.ZERO;

    BigDecimal baseAmt = contract.getBaseAmount() != null
        ? contract.getBaseAmount() : contract.getContractAmount();
    BigDecimal benefitAmt = contract.getBenefitAmount() != null
        ? contract.getBenefitAmount() : BigDecimal.ZERO;

    BigDecimal completedBaseSum = stages.stream()
        .filter(s -> STAGE_COMPLETED_STATUSES.contains(s.getStageStatus()))
        .map(ProjectStage::getStageOutput)
        .reduce(BigDecimal.ZERO, BigDecimal::add);

    BigDecimal completedBenefitSum = stages.stream()
        .filter(s -> STAGE_COMPLETED_STATUSES.contains(s.getStageStatus()))
        .map(ProjectStage::getBenefitInclusionRatio)
        .reduce(BigDecimal.ZERO, BigDecimal::add);

    BigDecimal baseExpected = baseAmt.multiply(completedBaseSum).divide(BD_100, 2, HALF_UP);
    BigDecimal benefitExpected = benefitAmt.multiply(completedBenefitSum).divide(BD_100, 2, HALF_UP);

    return baseExpected.add(benefitExpected);
}
```

**重要**：`stages.benefit_inclusion_ratio` 是**累计**比例（如阶段 3 是 30%，阶段 5 是 100%），所以"已完成阶段的 ratio 之和"会重复计算。需要改成**取已完成阶段中最大的累计%**：

```java
BigDecimal latestCompletedBenefitRatio = stages.stream()
    .filter(s -> STAGE_COMPLETED_STATUSES.contains(s.getStageStatus()))
    .map(ProjectStage::getBenefitInclusionRatio)
    .max(BigDecimal::compareTo).orElse(BigDecimal.ZERO);
```

`stage_output` 同理 — 现在它也是累计%（看示例：阶段 1=3%，阶段 2=46%，阶段 2 完成=100%）。

**统一原则**：所有"完成阶段的比例"都是累计值，**取最大**而不是求和。

## 六、效益修正模块（新增）

### 6.1 后端

**Service / Controller**：
- `ContractBenefitRevisionService` — `revise(contractId, newAmount, reason, isFinal, userId)`
- `POST /contract/{id}/benefit-revision`
- `GET /contract/{id}/benefit-history`

**业务逻辑**：

```java
@Transactional
public Long revise(Long contractId, BigDecimal newAmount, String reason,
                    Boolean isFinal, Long userId) {
    Contract c = contractMapper.selectById(contractId);
    if (c.getBenefitStatus() == 1) {
        throw new BusinessException("合同已最终结算，效益值不可修改");
    }

    BigDecimal oldAmount = c.getBenefitAmount();
    ContractBenefitRevision rev = ContractBenefitRevision.builder()
        .contractId(contractId)
        .oldAmount(oldAmount)
        .newAmount(newAmount)
        .deltaAmount(oldAmount == null ? null : newAmount.subtract(oldAmount))
        .revisionReason(reason)
        .isFinal(Boolean.TRUE.equals(isFinal) ? 1 : 0)
        .operatorId(userId)
        .build();
    revisionMapper.insert(rev);

    c.setBenefitAmount(newAmount);
    if (Boolean.TRUE.equals(isFinal)) c.setBenefitStatus(1);
    contractMapper.updateById(c);

    return rev.getRevisionId();
}
```

## 九、迁移与兼容性

### 9.1 已有 v0.2 数据处理

- **v0.2 已创建的产值分配单**：保留，标记 `legacy_flag=1` 表示按旧公式（60%/40%）。报表口径如需精确，按 flag 区分。
- **新建分配单**：走 v0.4 公式

  - 报表显示时若读旧记录的 `leader_extra`，加到"公司账"展示即可

### 9.2 合同数据兜底

- v0.2 已有的合同：`base_amount`、`benefit_amount` 可能为 null
- 计算时兜底：
  - `baseAmt = contract.base_amount ?? contract.contract_amount`（基本收费类型回退到合同金额）
  - `benefitAmt = contract.benefit_amount ?? 0`
- 这样 contract_type=0 的固定收费项目无需迁移

### 9.3 阶段数据兜底

- v0.2 阶段实例的 `benefit_inclusion_ratio` 默认 0
- 已有项目如果是 `contract_type=1`：
  - 财务需要逐项目人工填写每个阶段的 `benefit_inclusion_ratio`
  - 提供批量导入工具（Excel）减负

## 十一、风险与注意事项

### 11.1 比例对调的影响（**最关键**）

- v0.2 已经在生产用过的话：员工已经按 60% 池分过钱，对调后会突然变成 40%
- 必须确认：**v0.2 数据是否真的进过财务流程**？如果只是测试数据，**清空重做**最干净
- 如果已经发过钱，需要：
  - 旧分配单加 `legacy_flag=1`
  - UI 上"历史 v0.2 单"按旧公式展示
  - 新单按 v0.4 公式

**强烈建议**：**正式投产前清掉所有 v0.2 测试数据**，避免长期维护两套公式

### 11.2 修正机制的负产值场景

- 如果效益值大幅下调（25 万 → 10 万），后续阶段累计可能小于已分配累计
- 例：已分配累计 24 万，效益降到 10 万后，累计变成 10 + 10 = 20 万 → 本期 = 20 - 24 = **-4 万**
- 处理：
  - 不阻止创建（因为业务真实如此），但要财务**显式确认**
  - 数据库 `total_amount` 允许负数
  - 员工实得也是负数 → 实际发钱时回收（绩效还原表标 `is_clawback`）

### 11.3 阶段累计比例的管理

- 用户答 A 选项 1：阶段比例**配在每个项目阶段实例上**——每新建项目都要财务配 5+ 个阶段的两组比例
- 工作量大但灵活
- 缓解：项目阶段模板（`project_stage_template`）建议加 `default_base_ratio` / `default_benefit_ratio`，新建项目时拷贝；财务可微调

**v0.4 不强制做模板默认值**（节省工作量），但建议 v0.5 补上

### 11.4 效益修正可见性

- 修正会改变本阶段产值 → 影响员工奖金 → 必须**留痕**
- `contract_benefit_revision` 表是审计依据，**不可删**
- UI 修正按钮**只给财务角色**（v0.5 角色权限上线后）

### 11.5 离职兜底独立字段

- 数据库保留 `output_value.other_amount`（离职兜底）
- 业务上钱进公司账，但报表上能独立看到"因离职没发出去的钱"
- 这样以后业务变化（如离职兜底改成给团队），改起来方便

### 11.6 守恒校验

新等式：

```
total_amount = Σ员工实得 + company_reserve
            （company_reserve = 60% + 降档差额 + 离职兜底）
```

旧的 v0.2 等式：

```
total_amount = company_reserve + Σ员工实得 + leader_extra + other_amount
            （4 项独立）
```

**新代码里 `leader_extra` 始终 0**；`other_amount` 仅作记录字段，不参与守恒和。
